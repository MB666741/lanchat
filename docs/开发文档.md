## 1. 五分钟上手

第一次打开：

1. 界面上先让你 **设置昵称**（聊天时用来分辨谁是谁）；
2. 同时在本机生成 **身份密钥对**（Ed25519），保存到 `~/.lanchat/identity.json`；
3. 界面上显示你的 **身份指纹**（如 `AB3F-91C2-77DE-0A55`）—— 这就是你的"身份证号"。

然后：点 **➕ 添加联系人** 看局域网里自动搜索到的人 → 选中点 **发送加好友请求** →
对方在 **🔔 新朋友** 里点 **同意** → 双方自动建立加密会话 → 开聊。

> 打包版就是双击 **`dist\LanChat\LanChat.exe`**；想从源码跑，注意文件名里有下划线：
> **`chat_gui.py`**（`chatgui.py` 是等价的别名文件）。

## 2. 自测模式（只有一台电脑也能验证）

```bash
python chat_gui.py --self-test
```

它会在这台机器上启动**两个完整独立的实例**（"甲"和"乙"），**每个实例都有一个和正常使用
一模一样的窗口**：联系人列表、添加联系人、新朋友、右键菜单、设置、文件传输全都在。
你在一个窗口点「➕ 添加联系人」发请求，在另一个窗口点「同意」，走的就是真实流程。

* 两个实例各有自己的身份密钥、好友列表、TCP 端口和数据目录，互不影响；
* 两个窗口**左右并排**放在屏幕上，不会互相压住；
* **不做任何预设、不自动替你操作**：想试验证问题，就自己在一个窗口右键对方 →「设置验证
  问题」，然后在另一个窗口发请求、答题；想试封禁，就自己点封禁。看到的现象和两台电脑互聊
  完全一致。加好友请求会出现在**另一个窗口**的 `🔔 新朋友 (1)` 里。
* 两个窗口是**靠真实广播**互相发现的（和两台电脑一样），程序**不会**预先替你登记对方地址；
  启动后最多等 9 秒，广播实在不通才兜底登记一次（那种情况下聊天/传文件照旧，但『隐身』
  在自测里看不出效果，窗口里会写明）。
* 启动日志里会打印两个实例互相看到的地址和来源
  （`自测模式: 甲(本机) 看到的 乙(本机) = 192.168.31.223:52344 (来源: 广播发现)`）；
  端口是 0 或者"没有登记上"就说明自测环境有问题（`--diagnose` 会一起检查）。
* 自测窗口顶上多一个 **『🧪 掉线 6 秒』** 按钮（只有自测模式有）：点下去这个窗口会**真的**
  下线 6 秒 —— 关掉监听、停掉广播（发 bye）、断开所有会话 —— 然后自己回来。对面窗口会先显示
  "对方不在线"，到点自动重连；这期间你发的消息会先存在本机，对方一上来就按"新消息"送达。
  一个按钮把"掉线 → 离线提示 → 自动重连 → 补发/补发记录"整条链路验完。

想只验证图形环境能不能出窗口，用 `--window-test 15`（15 秒后自动关）。

* 左侧标记：`🔒` 已加密连接、`🔑` 通道已建立但还不是好友、`○` 好友离线、

* 右上角 `✋ 回答问题 (①)`：有人给你出了验证问题时变成橙色并显示条数，点一下就能答题。

* **右键联系人**：发送文件 / 重新连接 / 取消加好友请求 / 设置验证问题 / 删除好友 / 封禁此人 / 解除封禁。
* 回车发送，Shift+回车换行。

## 4. 加好友的完整流程

```
        小明                                     小红
  ① 点「添加联系人」看到小红（UDP 广播自动发现在线的人）
  ② 点「发送加好友请求」  ──────────►    ③ 若小红设了验证问题: 先给小明出一道题
  ④ 弹窗答题 (答错到上限 -> 小红自动封禁; 答对才继续)
  ⑤ 小红「🔔新朋友」出现请求 (含对方指纹/附言)  ──► 点「同意」/「拒绝」/「封禁」
  ⑦ 变成好友, 建立加密会话 ◄──────────    ⑥ 同意后立刻(或对方上线后)自动建立加密会话
  ⑧ 双向聊天、传文件 (全部 AES-256-GCM 加密)
```

* **同意之前**：只是"陌生人/等待验证"，聊天发不出去。即使加密通道已经建立，
  也只允许传"加好友请求"这一种元数据，聊天内容一律被拒绝。
* **拒绝**：请求方收到"对方拒绝了你的好友请求"，可以直接再申请（不是拉黑）。
* **删除好友**：删除时会**通知对方**，对方那边也会把这条联系人移除并提示
  "xxx 把你从好友里删除了"。只断连接不通知的话，对方会以为还是好友、一直重连，
  发出去的消息其实一条也到不了（用户报过这个现象，已修）。
* **封禁**：对方之后发来的请求和连接在**握手阶段**就被拒收；在「⚙ 设置 → 黑名单」
  里可以随时 **解除封禁**，解禁后对方能重新申请。
* **核对身份**：同意前可以点开「设置」把双方的指纹对一遍（微信/QQ 的"安全码"同理），
  指纹一致说明中间没有人冒充。

### 4.1 加好友验证问题（可选）

规则很简单：**谁要被加，谁出题**。小红出题 → 小明来加她时必须答对，答错到上限被小红自动封禁。

* **出题**：小红在「➕ 添加联系人」里选中"小明"这个局域网用户，填好"问题 + 答案 + 答错上限"，
  点 **给选中的人出题**；也可以右键左侧已有联系人 →「设置验证问题」。
  **出题人随时能反悔**：同一个界面上点 **『取消出题』**（会显示当前给他出的是什么题），
  或者右键联系人 →「设置验证问题」→「取消设题」。取消后对方再申请就不用答题了。
* **答题**：小明点了"发送加好友请求"之后，**会自动弹出一个答题窗**；关掉了也没关系，
  随时点右上角 **✋ 回答问题** 或「添加联系人」里的 **✋ 回答问题** 就能继续答
  （**不需要先在列表里选中谁**）。
* **答错当场就知道**：提交后弹窗**不会关掉**，对方校验完立刻在弹窗里显示
  "❌ 答案不对，还剩 N 次机会"，改一下点『再交一次』就行；答对了显示
  "✅ 答案正确" 并自动关窗。对方一直没回话（可能掉线）也会提示。
* **不想答 / 对方已经下线**：答题窗里有 **『取消加好友请求』**，右上角菜单（右键联系人）里也有
  同名菜单项。点了之后对方那边这道题作废、连接断开，以后想加重新发请求即可。
* **答错**：还剩几次机会会写在聊天窗口里；到上限后小红自动封禁小明。
  小红解禁后，小明**再点一次"发送加好友请求"**就会拿到一道**新的题**，可以重新作答。
* **答对**：小明的请求才会出现在小红的「🔔 新朋友」里，并标注"已通过验证问题"。
* **题目按"人"保存，不跟好友关系走**：小红把小明删了（或者拒绝了他），小明再加回来
  **必须重新答题**；小红改了题目，之前答对过的人也要重新答。只有"还是好友"时才不用重复答题。

安全性质：

* **答案永远不上网，也不落盘明文**，硬盘上只有 `盐 + 派生密钥 K = PBKDF2(答案, 盐)`；线上只有
  "题目 + 一个随机数 + 一个一次性证明"；答案明文连内存里都不留；
* 每次提问都用**新的随机数**，同一个答案每次的证明都不同，抓包**无法重放**；
* 校验直接用落盘的 K 算证明，所以**程序重启之后依然能正确判定**（旧版把答案只放在内存里，
  重启后会把答对的人当成答错，一路错到自动封禁——已在修复记录里）；
* 想绕过（离线穷举答案）要付 **20 万次 PBKDF2 迭代/候选** 的成本，在线爆破会被答错上限直接封掉；
* 校验用 `hmac.compare_digest` 常量时间比较，避免时间侧信道。

协议：出题方保存 K 后，发 `question-challenge{question, salt, nonce, max_attempts}`；
回答方算 `proof = HMAC(K, "lanchat/v2/answer-proof" | nonce)` 回 `question-answer{proof}`；
出题方用存下来的 K 算同一个 proof 比对。见 `lanchat/crypto.py` 的
`answer_key / answer_proof / answer_proof_matches_key`。


## 5. 软件原理

### 5.1 总览

```
                    ┌───────── UDP 广播 (自动发现) ─────────┐
                    │ 每 3 秒广播: 我是谁/叫什么/我的TCP端口  │
                    ▼                                      ▼
        ┌────────────────────┐                  ┌────────────────────┐
        │  电脑 A (小明)      │◄── TCP 加密长连接 ─►│  电脑 B (小红)      │
        │  UDP 50505 收广播   │   握手/聊天/文件    │  UDP 50505 收广播   │
        │  随机 TCP 端口      │                  │  随机 TCP 端口      │
        └────────────────────┘                  └────────────────────┘
```

### 5.2 自动发现（无需填 IP）

* 每台机器监听**同一个 UDP 端口**（默认 50505），绑定 `0.0.0.0` 并开启地址复用，
  因此同一台机器开多个实例也能互相看见。
* 每 3 秒向本网段的 **定向广播地址**（由网卡 IP + 子网掩码算出，跨平台探测）发一个 beacon：

  ```json
  {"t":"lanchat","v":2,"k":"beacon","id":"lc-3f2a…","name":"小明","port":54021,"dport":50505,"ts":1730000000}
  ```

  `k:"who"` 是**单播探测**（"你在吗"，见 5.2.1）：收到的一方会**单播回**一条 `k:"beacon"`，
  回包发到探测方声明的 `dport` 上。`k:"bye"` 表示退出。

* 收到别人的 beacon 就登记为"在线"，12 秒没消息就标记离线；改名会立刻重播。
* 因为**广播不会跨网段**，所以"看得见"就等于"在同一局域网"，不用手填 IP。
* 聊天的 TCP 端口由系统随机分配（beacon 里带上真实端口），避免端口冲突。

**哪些网络能自动发现**（关键看这张网跑不跑二层广播）：

| 网络 | 自动发现 | 说明 |
| --- | --- | --- |
| 同一个局域网 / Wi-Fi、同一台机器多开 | ✅ | |
| Radmin VPN、Hamachi、ZeroTier（默认 L2 模式） | ✅ | 都是虚拟二层网络，广播会在同一个虚拟网络内转发 |
| OpenVPN 的 **tap**、Hyper-V/VMware 的仅主机网络 | ✅ | 同样是二层 |
| **Tailscale、裸 WireGuard、OpenVPN 的 tun、Netbird** | ❌ | 三层隧道里**没有广播这个概念**，只能用下面的「手动添加」 |
| 跨路由/跨 VLAN 的不同网段 | ❌ | 广播不过路由器，这是设计如此 |
| 开了「客户端隔离 / AP 隔离」的 WiFi、访客网络 | ❌ | 中间设备直接丢弃广播 |
| 任意网络，但防火墙拦了 UDP 50505 | ❌ | VPN 网卡常被判成"公用网络"，第一次运行要点"允许" |

小程序自己会给**每张网卡**各算一个定向广播地址（不是只发默认网关那条）。用
`python chat_gui.py --diagnose` 能看到实际算出来的"本机地址 / 广播地址"，一眼就知道那张虚拟网卡有没有被算进去。

### 5.2.1 手动模式（广播不通时）

「添加联系人」底部有 **手动添加**，两种填法：

| 你填什么 | 程序怎么做 | 什么时候用 |
| --- | --- | --- |
| **只填 IP**（`100.64.0.7`） | 先发一个 **UDP 单播探测**问对方"你在吗"；对方**单播回**一条 beacon，里面带着它**当前随机的 TCP 端口** → 直接连过去 | 默认；双方都**不用**固定端口 |
| `IP:TCP端口`（`100.64.0.7:50606`） | 跳过探测，直接 TCP 连过去 | 对方开了『隐身』、或对方改了发现端口 |

单播探测打在对方的**发现端口**上：先试本机配置的那个，再补一个标准 `50505`（双方都改成同一个
自定义端口也能对上）。双方发现端口完全不一样时就探不到，退回填 `IP:TCP端口`。

```
只填 IP:  你 ──UDP 单播 "who"──► 对方:50505
          你 ◄──UDP 单播 beacon── 对方          (带着它真实的 TCP 端口)
          你 ──TCP 连接──────────► 对方:那个端口   → 加密握手
```

其他要点：

* **地址里的标点会自动纠正**：中文输入法下的中文冒号 `：`（U+FF1A）、全角数字 `５０６０６`、
  多打的空格、`192.168.1.5 50606`（空格当分隔符）、连反引号一起粘进来的 `` `IP:端口` ``、
  `http://IP:端口/` 都会被整理成 `IP:端口` 再用（真整理过时聊天区会写明"已自动整理地址"）。

* 只填 IP 时，探测阶段就直接拿到对方**真实身份**，连占位 id 都不需要；
  手填 `IP:端口` 时先登记成占位 `manual:IP:端口`，握手后自动迁移到真身份
  （`_adopt_real_identity`）。
* 手填的地址会**落盘**（`manual_address`），重启后照旧能重连。
* 连接由**添加方**负责维持：被添加方收到的是一次拨入连接，那个源端口是临时的、不能拿来反拨
  （所以程序也不会把它当成对方地址存下来）。想让对方也能主动连你，让他也手动加你一次
  （那时他需要你的 IP:TCP端口）。
* 广播能通的网络**完全不需要**这一节。

### 5.2.2 隐身（不允许被自动搜索）

⚙ 设置 → **允许被自动搜索**，关掉之后：

* **不广播** beacon → 别人在「局域网中的人」里看不到你；
* **不回应单播探测** → 别人只填 IP 也问不出你的端口；
* 别人只能 **『手动添加』填 `你的IP:你的TCP端口`** 来加你（端口在设置里能看到，
  建议顺便在『本机端口』里固定一个，免得重启后变了）；
* 你自己**仍然能看到别人**（照旧收广播）、也能正常聊天 —— 是"我能搜别人，别人搜不到我"。
* 状态栏会显示 **🕶 隐身中**，随时知道现在是哪种状态。

> **自测模式也能验它**：`--self-test` 的两个窗口**都开着发现层**，而且是**真的靠广播**互相看见的
> —— 启动时程序只会等广播（最多 9 秒），**不会**预先替你把对方塞进列表。所以：在甲窗口把
> 「允许被自动搜索」关掉，乙窗口的「局域网中的人」里甲会在 12 秒内消失（离线超时）；再打开就
> 又回来了。
>
> 如果所在网络里广播真的不通（只有 VPN 网卡 / 防火墙拦了 UDP），自测会在 9 秒后**兜底**用内部
> 登记让两个窗口互相可见，并在各自的聊天区里写明"广播不通，兜底登记；**隐身在这种情况下测不出来**"。
> 被兜底登记的人在列表里的状态列会显示 **手动登记** —— 它和"搜到的人"是两回事。




### 5.3 好友关系是一道独立的门

发现 ≠ 能聊天。关系状态保存在 `contacts.json`，共四种：

| 状态 | 含义 | 能不能聊天 |
| --- | --- | --- |
| `friend` | 好友 | ✅ 能 |
| `request-out` | 我发了请求，等对方确认 | ❌ 不能 |
| `request-in` | 对方请求加我，等我处理 | ❌ 不能（点同意后变 friend） |
| `blocked` | 被拉黑（两个方向分开记） | ❌ 不能，且被封方的连接在握手阶段就被拒，并收到明确的 `code=blocked` 原因 |

**封禁 ≠ 删除好友**：封禁只是"暂时拒收对方的消息和请求"，`friend_before_block` 会记住
"封之前是不是好友"。解禁时：是好友就**还是好友**（自动重连并通知对方"已解禁"），
不是好友就回到"陌生人"让对方重新申请 —— **绝不**造出一条没答过题的待处理请求。
想彻底断开请用『删除好友』（对方会收到提示）。

两个方向要分清：`blocked` 是"我封了他"（我拒收），`blocked_by_peer` 是"他封了我"
（只做记录，不能拿来拒收对方的连接）。

**授权来自"对方在我的好友名单里"，不是来自某条消息** —— 这样即使重新连接、换会话密钥，
权限判断也不会被绕过。

三类"状态变更消息"都要**回执**才算送达（见 5.6 节）：

| 消息 | 谁发 | 回执 | 收不到回执时 |
| --- | --- | --- | --- |
| `friend-request` | 申请方 | `friend-request-ack` | 每 5 秒重发（最多 6 次，然后转 30 秒例行重拨） |
| `friend-accept` | 同意方 | `friend-accept-ack` | 每次建/换会话都补发，直到确认 |
| `friend-unblocked` | 解禁方 | `friend-unblocked-ack` | 立刻试一次（没通道就拨号），之后每 5 秒重试 |

这些状态都落盘（`accept_pending` / `unblock_notice`），所以**对方离线也没关系**：他一上线就会补发。

### 5.4 线程模型

```
主线程 / GUI      : 界面、按钮、事件分发 (所有网络事件都经 queue 送进来)
tcp-accept        : 接受 TCP 连接，每个连接起一个握手线程
discovery         : 一个线程收 UDP 广播，定期发自己的 beacon
conn-manager      : 每 0.5 秒扫一遍：给离线好友重连(带退避)、重发没处理完的加好友请求
每条会话 3 个线程  : rx (收+解密+分发)、tx (从队列取密文写 socket)、heartbeat (心跳)
```

关键约束（都踩过坑，见 [修复记录](#11-修复记录)）：
**一条会话的明文→加密→入队必须在同一把锁里完成**，并且**所有帧（包括心跳）都走同一个
发送队列/同一个写线程**，否则密文会乱序，对端的 nonce 校验会直接判为重放。

### 5.5 一条消息的旅程

```
输入框回车
  → ChatService.send_text()         检查对方是好友且会话已认证
  → Connection.send_message()       在 _order_lock 里: 序列化 JSON → AES-256-GCM 加密 → 入队
  → 写线程 protocol.send_frame()    {"type":"enc","body":{"n":nonce,"c":密文}} + "\n"
  → 网络                             (中间人只能看到 base64 密文)
  → 对端读线程 read_frame()          按 "\n" 分帧
  → Connection._dispatch()           用会话密钥解密 + 校验 nonce 计数
  → _handle_message()                分类: 聊天 / 文件请求 / 文件分片 / 好友事件
  → ChatService 发出 ServiceEvent     经 queue 到 GUI 线程
  → 界面渲染气泡 + 未读 +1
```

### 5.6 帧格式（便于抓包调试）

明文帧（只在握手和心跳阶段出现）：

```json
{"type":"hello","v":2,"suite":"X25519-ED25519-HKDF-SHA256-AES256GCM","sid":"…",
 "purpose":"friend","card":{…身份卡…},"x":"临时公钥","nonce":"…"}
{"type":"proof","sig":"…"}          {"type":"error","reason":"…","code":"blocked"}
{"type":"ping"}                     {"type":"pong"}
```

`error` 的 `code` 是可选的机器可读原因（目前用到 `blocked`）：对端据此能明确显示
"你还在我的黑名单里"，而不是含糊的"连不上"。写这一帧之后会先把写方向半关闭
（`SHUT_WR`）并把对端可能已发来的数据读干净，最后才 `close()` —— 否则 `close()` 发出的
RST 会把这一帧一起冲掉，对方只看到"对方提前断开连接"。

加密帧（建立会话之后的**全部**内容）：

```json
{"type":"enc","body":{"n":"nonce(base64)","c":"密文(base64)"}}
```

`body` 里的明文是应用层消息：`{"t":"chat","text":"...","seq":第几条}`、`{"t":"file-offer",...}`、
`{"t":"file-chunk","body":{...}}`、`{"t":"friend-request","...}`、
`{"t":"friend-unblocked",...}`（对方解禁通知）、`{"t":"history-state"/"history-replay",...}`
（本会话聊天记录的对账与补发，见 5.7）等。加好友还没确认的会话里只放行
"谈加好友"的那几种类型（`connection._PENDING_ALLOWED`），别的一律拒绝。

**加密前会先做长度混淆**：明文里被塞进一个随机长度的 `p` 字段，让密文长度落在固定的档位上
（见 6.5）；解密后这个字段会被丢掉，所以上面的消息格式里看不到它。

几条"必须有回执"的消息（`…-ack`）：`friend-request` / `friend-accept` /
`friend-unblocked`。它们都是**幂等**的，收不到回执就按固定间隔重发 —— 会话在建立
的一瞬间被去重拆掉、对方恰好离线，这些情况下"发出去"并不等于"对方收到了"。

### 5.7 聊天记录：本会话内保留 + 重连补发（关掉就没）

聊天内容**不落盘**（故意的：你选的是"关后即焚"）。但程序运行期间它不再只活在界面那个
文本框里 —— 服务端按人记一份内存记录（每人最近 500 条），于是：

* **切换联系人再切回来**，刚才的对话还在（以前会被清空）；
* **一方重启、另一方还开着** → 还开着的那一方把这段对话**补发**回去，重启方的聊天区
  就又能看到之前的对话（连"自己当时说过的话"也会补回来，因为对方手上也留着）；
* **对方离线时发的消息不会直接丢**：先记在本机，等他一上线就跟历史一起补过去；
  其中"当时没送出去的"到了对方那边**按新消息算**（有未读提示），纯历史则只补不打扰。

对账协议（都是加密帧，身份未确认前不交换）：

```
通道建立 (双方是好友) → 各自发  {"t":"history-state","in":我这收到你第几条,"out":我自己发到第几条}
收到对方的对账        → 我把自己这边"他缺的"分帧发回
                        {"t":"history-replay","entries":[{"from":谁,"seq":第几条,"ts":时间,"text":内容,
                                                          "pending":true(当时没送出去才带)}]}
重复/重连也不会重复显示：小于等于"已知序号"的条目直接丢弃。
```

**补发不需要"旧密钥"**：内存里存的是**明文**，补发时是用**当前**这把会话密钥重新加密的
（再叠加长度混淆）。所以密钥轮换"用完就丢"这条规则完全不受影响 —— 网络上从头到尾只跑
新密文，没有任何一帧是旧密钥的产物。

边界（都写在代码注释里）：

* 只有在线的**那一方**手上才有那份记录 —— 双方都退出，对话就彻底没了（这是设计目标）；
* 补发的是**文本**，文件不重传（重传大文件不合适，文件本身已经存到接收目录里了）；
* 对方程序如果被杀掉/断网时正好有消息在途，那一条可能两边都没有 —— 记录是"尽力而为"，不承诺像服务器那样可达。

## 6. 加密原理（对照 HTTPS）

| HTTPS / TLS | 本工具 |
| --- | --- |
| 服务器证书里的 ECDSA 密钥 | 启动时生成的 Ed25519 **长期身份密钥**（落盘保存） |
| 握手时的 ECDHE 临时密钥 | 每次连接新生成的 X25519 **临时密钥对** |
| CertificateVerify 签名 | 对整段握手记录（双方临时公钥 + 身份卡 + 会话号）的 Ed25519 签名 |
| Finished / 密钥派生 | **HKDF-SHA256 → 双向 AES-256-GCM** 会话密钥 |
| 证书指纹校验 | 加好友时展示并记录对方的 **密钥指纹**，可人工核对 |

### 6.1 握手时序（每次连接都重新走一遍）

```
小明                                                    小红
 │ hello: 会话号 + 临时X25519公钥 + 随机数 + 我的身份卡      │
 │────────────────────────────────────────────────────────►│
 │ hello: 同样内容 (含小红身份卡)                            │
 │◄────────────────────────────────────────────────────────│
 │ ① 双方各自验证身份卡自签名, 且 peer_id == SHA256(公钥)     │
 │ ② ECDH(我的临时私钥, 对方临时公钥) → 共享秘密 shared       │
 │ ③ HKDF(shared, salt=会话号+握手摘要) → 64 字节 → 双向密钥  │
 │ proof: 用长期 Ed25519 私钥签握手摘要                       │
 │◄───────────────────────────────────────────────────────►│
 │ ④ 互相验签通过 → 之后全部走 AES-256-GCM 密文               │
```

### 6.2 密钥派生链

```
身份: Ed25519 长期密钥对 (落盘)          每连接: X25519 临时密钥对 (用完即弃)
                     │                                │
                     │ 签名握手摘要                    │ ECDH
                     ▼                                ▼
             ┌──────────── 握手记录 (transcript) ─────────────┐
             │ hello_I{card,x,nonce} + hello_R{card,x,nonce}   │
             └───────────────────────┬─────────────────────────┘
                                     ▼
       shared = X25519(临时私钥, 对端临时公钥)         ← 前向保密的来源
                                     │
       HKDF-SHA256(shared, salt=SHA256(sid‖transcript), info="lanchat/v2/session-keys")
                                     ▼
       64 字节 → 拆成两把 32 字节密钥 (发起方→接收方 / 接收方→发起方)
                                     ▼
       AES-256-GCM, nonce = 4字节随机会话前缀 ‖ 8字节递增计数器,
       AAD = sid ‖ 排序后的双方 peer_id   (绑定会话与身份, 防止密文被搬走)
```

### 6.3 密钥轮换（KeyUpdate，默认每 30 条消息一次）

会话密钥不是"一条连接一用到底"：每收发 `--rekey-after`（默认 30）条消息就会换一轮。
这样即使某个中间人日后破解出某一轮密钥，**也只能解开那一小段对话**。

**传文件会额外换两次**：对方**同意接收**的那一刻换一把新密钥（文件这一大串数据不用聊天那把），
文件**传完**（收方校验 SHA256 之后）再换一把，把传文件用的那一轮直接退役。于是"传了一个
大文件"这件事最多只影响那一轮密钥，前后聊天都是另外的密钥。任意一方都能发起这个请求
（`rekey-request`）：真正的轮换仍只由固定的"发起方"执行，否则两边各用自己的随机数派生会岔开。

```
发起方                                    接收方
 │ begin(fresh): 用【旧】密钥加密           │
 │───────────────────────────────────────►│  收到 begin: 立即切到新密钥
 │ 继续用旧密钥发消息 (在途, 稍后到达)       │  用【旧】密钥回 accept
 │◄───────────────────────────────────────│
 │ 收到 accept: 切到新密钥                  │
 │ (旧密钥保留 5 秒宽限期, 专门用来解在途消息) │ (同样保留宽限期)
```

* 新密钥由 `HKDF-SHA256(共享秘密ECDH, salt=会话号+轮次+fresh, info=角色)` 派生，
  **双方各自算出、网络上一个字节的密钥材料都不传**；
* 双方都用同一份 `fresh` 和"角色"标签区分方向（`i2r` / `r2i`），所以两端结果天然互补；
* 切换后旧密钥立即作废（只留 5 秒宽限期处理在途消息）；
* 随时可在「⚙ 设置 → 密钥轮换」改成别的条数，或填 0 关闭。

这条协议有三条硬规则，每一条都是踩坑换来的（违反任何一条都会让两边密钥岔开、
之后每一帧都"密文认证失败"然后掉线）：

| 规则 | 为什么 |
| --- | --- |
| 收到 `accept` 必须把这次轮换**收尾**（清掉 `_rekey_outstanding`） | 否则状态机卡死：轮换一两次后再也不轮换，最后 10 秒超时触发"单方面换密钥" |
| **绝不单方面换密钥**：只有收到对方的 `begin`/`accept` 才切 | 单方面切换 = 对方还在旧密钥上，两边立刻岔开。回执没到就**重发 `begin`**（幂等），而不是自己先切 |
| 自动轮换只由**一方**发起（按 peer_id 定，两边算法一致） | 两边同时 `begin` 会各用各的 `fresh` 派生出不同的新密钥，直接岔开 |
| 在途的**文件分片内容**也要有旧密钥兜底 | 分片是"内容二次加密 + 外层信封"，只给信封兜底的话，换密钥瞬间正在传的大文件会中断 |

`tests/test_rekey.py` 现在验证：连续 40 条消息**每一次轮换都真的发生**（不是只轮换一两次）、
顺序内容全对、双向同时对轰 epoch 始终一致、**频繁轮换期间传 2MB 文件 SHA256 一致**；
`tests/test_self_test_mode.py` 另外验证"连着发 140KB + 12MB 两个文件不断线"。

### 6.4 安全性质一览

| 威胁 | 处理方式 |
| --- | --- |
| 抓包偷看聊天/文件 | 全部 AES-256-GCM 密文；聊天和文件分片都加密；网络层只有 `type=enc` |
| 冒充别人 | `peer_id = SHA256(Ed25519 公钥)` 不可伪造；身份卡带自签名；好友会话里 peer_id 必须与记录一致 |
| 中间人替换临时公钥 | 双方对"两个临时公钥 + 双方身份卡"整体签名，改动任何一项验签失败 |
| 旧密钥泄露后解密历史 | **前向保密**：会话密钥来自一次性临时密钥，握手后即丢弃 |
| 一次连接被长期监听 | **密钥轮换**：每 30 条消息换一轮，破解一轮也只能解开一小段 |
| 陌生人随便加好友 | **验证问题**（可选）：答对才能进入请求列表，答错到上限自动封禁 |
| 抓包重放验证问题的答案 | 每次提问换新随机数，线上只有一个一次性的 HMAC 证明；答案和派生密钥都不上网 |
| 重启后把答对的人当成答错 | 校验只用落盘的派生密钥 K（`answer_proof_matches_key`），不依赖内存里的答案明文 |
| 重放 / 乱序旧报文 | 每条会话独立随机 nonce 前缀 + 递增计数器 + 重放窗口（容忍乱序、拒绝重复） |
| 密文被篡改 | AES-GCM 的 AAD 绑定会话号和双方身份，认证失败直接断开 |
| 伪造身份卡 | 身份卡必须自洽（签名有效 + peer_id 与公钥匹配），否则握手阶段就拒绝 |
| 不想理的人反复骚扰 | 封禁：握手阶段直接拒收，对方只看到"你已被对方封禁" |
| 超大报文打爆内存 | 单帧 8 MiB 上限；文件按 256 KiB 分片流式传输；收完校验整文件 SHA256 |
| **从"包多大"猜出你在干嘛** | **长度混淆**（默认开）：明文按 512 字节的"桶"随机补齐再加密（见 6.5），于是"3 个字的闲聊"和"半屏文字"的密文长度落在同一两个档位，同样内容的两次发送长度也不一样 |

### 6.5 长度混淆（padding）+ 压缩：包大小也要藏起来

密文长度基本等于明文长度，所以"解不开内容"并不等于"看不出你在做什么"：**几个字的闲聊**、
**一大段历史补发**、**一个长文件名**，包的大小完全不一样，抓包的人一眼能分类，甚至能猜出
你打了多少字。所以发送前会做两步加工（都在加密之前）：

```
明文 {"t":"chat","text":"你好","seq":1}
 ① 按需压缩: 重复内容用 zlib 压小 (只在不吃亏时才用)   → 小的消息这一步跳过
 ② 随机插: 补齐到一个步长 (512B) 的整数倍, 再**随机**加 0~一整个步长的字节
密文 ≈ 上面这个长度 → 抓包的人只看到"几百到一千多字节的包", 且**每次都不一样**
```

* 关键是"**每次随机插**"而不是"都凑成同一个大小"：同一条消息连发 20 次，线上会出现近 20 种
  不同长度（实测 18/20），固定长度本身就是指纹；
* 同一步长内的消息（1 个字 ~ 200 字）密文大小只差几十~几百字节（实测窗口 288 字节），
  看不出你到底打了几个字；
* 填充内容来自 `os.urandom`，和正文一起被 AES-GCM 加密并认证 —— 不可预测，改一个字节都过不了校验；
* 解密侧自动丢掉填充、解开压缩（`crypto.decrypt_message`），上层拿到的消息和原来完全一样；
* 明文超过 16 KiB（文件分片那种）**不补也不压**：补了盖不住"我在传大文件"，压了是白费 CPU；
* 历史补发另外做了两件事：**每帧最多 80 条**、多帧之间**随机间隔 50~250 毫秒**在后台线程发，
  不是"一发一大串"——否则密集的大包本身就是"正在同步历史"的招牌。

**压缩会不会反而泄露？**不会（不会重演 CRIME/BREACH）：那是"攻击者注入的内容和秘密被放在
同一段里反复压缩"才会有的长度预言机；这里是**逐条消息独立压缩**，一条消息只由一方写，
攻击者没法把自己猜的内容塞进同一段压缩流里。

**它挡不住什么（重要）**：补齐只能向上取整，**盖不住总量和时间**——一个观察者仍然知道
"你们在通信""这会儿传了大约 N KB"。真要连这个都藏，得上恒定速率填充（一直在发垃圾流量），
那对局域网小工具来说代价太大。所以：**长度混淆是"降低可分类性"，不是"隐身"**。

**已知边界**：加好友是"人工确认指纹"的信任模型 —— 第一次和陌生人建立连接时，身份只经过
指纹展示，需要你自己核对（与微信对比安全码同理）。局域网内的攻击者仍可做**流量分析**
（知道谁和谁在通信、大概传了多少数据）；长度混淆只是让"从包大小猜内容"这件事失效。
对方**离线且本地没有记录时**发不出去（本会话内由持有记录的一方补发，见 5.7）。

**掉线重连的说明**：连接断开后会自动重连并**重新握手（新的一次性密钥）**，
所以重连本身也是一次密钥彻底更换。

## 7. 文件传输

```
发送方                                          接收方
 file-offer (名字/大小/SHA256)  ──────────────►  弹窗询问(或自动接收)
                                                   ↓ 同意
 等待 file-accept               ◄──────────────  file-accept
   ↓ 收到同意后才开始推数据
 file-chunk × N (每个分片独立加密) ────────────►  写入文件 + 边收边算 SHA256
 file-end                        ─────────────►  关闭文件 → 比对 SHA256 → 提示结果
```

* **必须对方同意才开始传**，所以拒绝不会浪费带宽（早期版本是边推边等，已修）。
* **传输时有进度条**：输入框下面会出现一根进度条，同时显示
  `发送 x.png: 43% (5.4 MB/12.1 MB) · 1.2 MB/s · 剩余约 6s`；传完显示"完成 + 平均速度"后自动收起。
* **只有一个统一的接收目录**（在「⚙ 设置 → 我的接收目录」里改，可一键打开），所有收到的文件
  都存这里；收到文件时的弹窗是三个按钮 ——
  **『📥 接收 (存到我的接收目录)』**、**『📂 另存到别处…』**（临时改到别处，目录+文件名随意，
  选完立刻开始接收，下次默认打开你上次选的目录）、**『拒绝』**。目标已存在时自动改名，不覆盖。
* 只有在「⚙ 设置」里勾了 **自动接收文件** 时才不弹窗（直接存到接收目录），
  这时也会在 `📢 通知` 里留一条"自动接收 xx → 存到哪"。自测模式默认**不**自动接收。
* 分片 256 KiB；明文加密 + base64 后单帧仍远小于 8 MiB 上限。
* 同名文件自动加 `(1)`、`(2)`，不覆盖已有文件；文件名做了安全处理（去掉路径分隔符）。
* 落盘后校验整文件 SHA256，不一致会明确提示"校验失败"。

## 8. 数据目录与持久化

| 文件 | 内容 |
| --- | --- |
| `~/.lanchat/identity.json` | 本机长期身份私钥 + 昵称（删掉它 = 换了个人，别人要重新加你） |
| `~/.lanchat/contacts.json` | 好友列表、待处理请求、黑名单、未读、最后一条消息 |
| `~/.lanchat/settings.json` | 自动接收文件、自动连接好友、密钥轮换频率、**我的接收目录**、给谁出过的验证问题 |
| `~/.lanchat/last-run.log` | 启动日志（带时间戳，排查用） |
| `~/Downloads/` | 接收到的文件（**默认就放在系统下载目录**） |

**聊天内容是唯一"不落盘"的东西**（见 5.7）：关掉程序就没了，只有运行期间记在内存里，
用来在对方重启/重连后把这段对话补发回去。想要"关了还在"的长期记录，目前是刻意不做的。

接收目录默认就是系统的**下载目录**；可用「⚙ 设置 → 我的接收目录」改成任何地方（改完立刻生效，
也会记住下次）。在只读环境里会自动降级：`~/Downloads` → `~/Downloads/lanchat` → 当前目录 →
临时目录，并在启动日志里提示。

## 10. 常见问题与排查

### 运行了但"没有反应"？按顺序做这 4 步

```bash
python chat_gui.py --diagnose        # 1) 环境自检 (含"能不能创建并显示窗口"实测)
python chat_gui.py --window-test 15  # 2) 只弹一个测试窗口, 15 秒后自动关闭
python chat_gui.py --self-test       # 3) 自测模式, 一台电脑验证全流程
type %USERPROFILE%\.lanchat\last-run.log   # 4) 启动日志 (带时间戳, 能看到卡在哪一步)
```

| 现象 | 原因 / 处理 |
| --- | --- |
| **双击 exe 后（或填完昵称点『开始使用』）卡住几秒** | 已修：以前建发现层时会在**界面线程**里同步跑一次 `ipconfig`（打包后的窗口程序里要 1.5~2.5 秒，源码运行只要 0.04 秒），Windows 就把窗口画成"未响应"。现在这份枚举有缓存、并且只在后台线程里做（详见修复记录 67）。如果还是慢，看启动日志里有没有 `⚠ 枚举网卡用了 N 秒` |
| 「添加联系人」里一个人都没有 | 对方没启动；不在同一网段/Wi-Fi；Windows 防火墙拦了 UDP —— 第一次运行要允许"专用网络" |
| 点了"发送加好友请求"，对方那边**没有提示** | 请求是异步发的：2.5 秒内发不出去会**直接弹窗**告诉你原因（比如"对方不在线"）。收到请求的一侧要打开 `🔔 新朋友` 才有"同意/拒绝"。自测模式请确认日志里的登记地址不是 `:0` |
| 「添加联系人」窗口按钮显示不全 | 已修（窗口按内容自适应高度，按钮先占位）。若你改过界面代码，请保持"固定区块先 pack、列表最后"的顺序 |
| 一直是"等待验证" / 连不上 | 对方还没同意；或对方离线（上线后自动重连）；防火墙拦了 TCP |
| **对话开着还是一直显示未读 (1)** | 已修（修复记录 72）：对话开着时不再攒未读；切走/关窗之后新消息才重新计数 |
| 对方同意了但发不出消息 | 看标题旁状态：`🔒 加密连接中` 才能发；`未连接` 时等自动重连或右键"重新连接" |
| 答错了验证问题 | 每次答错都会告诉你还剩几次；到上限会被对方自动封禁。对方解禁后，你**再点一次"发送加好友请求"**会拿到一道新题 |
| 明明输入了答案，却说没输入 | 已修（自测模式两个窗口时 Tk 变量绑错了窗口，输入框里看得到字但读不到）。现在弹窗也会先抢焦点，万一敲到聊天输入框里还会问一句要不要拿它当答案 |
| 对方不在线 / 不想答那道题 | 答题窗里点 **『取消加好友请求』**（或右键联系人 → 同名菜单），对方那边这道题就作废了 |
| 对面把我删了 / 把我封了 / 下线了，只看到"人没了" | 现在都会进 **`📢 通知`**（有未读数），被删/被封还会**直接弹窗**；好友离线在列表里写 **`[离线]`**，不会悄悄消失 |
| 收到文件时找不到"改保存位置"的入口 | 弹窗现在是三个大按钮：**接收 (存到我的接收目录) / 另存到别处… / 拒绝**；接收目录在「⚙ 设置」里改 |
| 答错验证问题没有任何提示 | 现在弹窗不关，就地显示"还剩 N 次机会"，可以直接改了再交一次 |
| 没弹窗、文件直接进了默认目录 | 说明「⚙ 设置 → 自动接收文件」是开着的（自测模式默认关）。关掉它就会每次问你；开着时也会在 `📢 通知` 里记录存到哪了 |
| 删了对方再加回来还要答题吗 | 要。验证问题按人保存，不跟好友关系走；只有还是好友时才不用重复答题 |
| 同一台机器开多个实例 | 可以，TCP 端口自动区分；只要 `--discovery-port` 相同就能互相发现 |
| 想让两组人互不干扰 | 各自用不同的 `--discovery-port` |
| 想重新开始（换身份） | 删掉 `~/.lanchat/identity.json` |
| exe 双击没反应 | 先看 `%USERPROFILE%\.lanchat\last-run.log`（或 `--data-dir` 指定的目录）；`dist\LanChat\LanChat.exe --diagnose` 用命令行跑能看输出 |
| 两边密钥轮换设置不一样 | 握手时协商：任意一方填 0 就不自动轮换，否则取更严格(更小)的那个；改设置会立刻通知对方一起生效 |

## 11. 修复记录

开发过程中踩过的真实坑，按发现顺序记录（现象 → 根因 → 修法），也方便以后回归检查。

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 文件传输到一半，接收方报"分片校验失败/检测到重放报文" | 心跳 `ping` 绕过发送队列**直接写 socket**，插到了排队中的文件分片中间；对端收到乱序密文，nonce 计数器判为重放 | 控制帧也走同一个发送队列/写线程（`Connection.send_control`） |
| 2 | 并发发消息时偶发对端解不开密文 | `send_message()` 里"加密取 nonce"与"入队"是两步，心跳线程/文件流线程/主线程交错，密文帧**乱序入队** | 取号 + 入队放进同一把 `_order_lock`；接收端改成"重放窗口"（容忍乱序、拒绝重复） |
| 3 | 拒绝接收文件后发送方还在继续推数据 | 发送方发完 `file-offer` 就立刻开始推分片 | 改成先等 `file-accept` 再开始传（`send_file` / `start_transfer`） |
| 4 | 上层收不到文件请求事件 | `_handle_payload()` 对 `file-offer/file-end/file-accept` 做了"连接层自己处理就 return" | 只有 `file-chunk`（大数据量）在连接层吞掉，其余全部上报给上层 |
| 5 | 双方同时发起连接时，唯一那条会话也被关掉 | 去重规则不对称：`keep_outgoing = my_id < peer_id` 在两侧语义相反，导致两条都被关 | 对称规则：`my_id < peer_id` 才保留自己主动发起的连接，另一方丢弃入站 |
| 6 | 从别的目录运行 `python D:\...\chat_gui.py` 报 `ModuleNotFoundError: No module named 'lanchat'` | 入口依赖当前工作目录 | 入口把**脚本所在目录**插入 `sys.path` |
| 7 | 运行后"没反应"：Windows 中文控制台抛 `UnicodeEncodeError: 'gbk' codec can't encode '\u26a0'` | 程序打印 `⚠ ✅ 🔒`，而中文控制台默认 GBK 编码，**打印时直接崩**（双击运行时一闪而过看不见） | 新增 `lanchat/console.py`，所有入口在**任何 print 之前**把 stdout/stderr 切成 UTF-8 |
| 8 | `.bat` 输出一堆 `'灞€鍩熺綉...' 不是内部或外部命令` | cmd.exe 把 UTF-8 编码的 .bat 当 GBK 解读，中文注释/`echo` 变成了命令 | `run_chat.bat` 内容改成**纯英文 ASCII**（非 ASCII 字节数 = 0）；中文名启动器只留一行 ASCII 转调 |
| 9 | `run_chat.bat` 说 `Cannot find Python`，但 `python` 明明能用 | 启动器只用 `where python` 判断 | 依次尝试 `LANCHAT_PYTHON` → `py -3` → `python` → `python3` → 常见安装目录 |
| 10 | **窗口其实开出来了，但被浏览器挡在后面**（用户以为"没反应"） | Windows 的"防抢焦点"机制：非前台进程调用 `SetForegroundWindow` 会被系统拦下 | 新增 `lanchat/winfocus.py`：`SetWindowPos(TOPMOST)` + `AttachThreadInput` + `SetForegroundWindow` + `FlashWindowEx` 闪任务栏；窗口短暂置顶 2.5 秒 |
| 11 | **运行 `python chat_gui.py`（不带 `--name`）时完全没有窗口** | 「设置昵称」是一个以**被 withdraw 的 root** 为父窗口 + `transient` 的 Toplevel，它一直是 `withdrawn / viewable=0 / 1x1`，而主流程在 `wait_window` 上**死等**它关闭 | 启动时先把主窗口显示出来，昵称直接画在主窗口里，用 `wait_variable` 等用户操作（事件循环不再被阻塞） |
| 12 | 关闭窗口后 Tk 报 `invalid command name "..._drain"` | `after` 定时任务在窗口销毁后仍触发 | 保存 job id，关闭时 `after_cancel` |
| 13 | 断线后**偶发**不再自动重连（要等很久或一直不恢复） | `_connect_once()` 在"已经连着/对方刚接受入站连接"时提前 `return`，但没把 `dial_state` 从 `connecting` 复位；连接管理器看到"正在连"就再也不重试 | 用 `try/finally` 保证任何退出路径都把 `dial_state` 复位为 `idle` |
| 14 | 自动化测试读不到启动日志，误判"窗口没显示" | Python 的 stdout 是块缓冲，子进程被 `terminate()` 时缓冲区内容丢失 | `startup_log.step()` 写完显式 `flush()` |
| 15 | 答对验证问题后点「同意」建不起加密会话 | 校验通过时没有记住那条通道，`accept_request` 找不到连接只能等下次重连 | 校验通过时保存 `contact.connection`；`accept_request` 发现没有活通道就立刻重连 |
| 16 | 反复出现 `用途不符 (对方声明 request)` 重连失败 | 握手用途（friend/request）由两边各自的状态机推导，状态不同步时双方声明不一致就被拒 | 统一规则："谁想建会话谁声明 friend，能认出对方就接受" |
| 17 | 密钥轮换后双方算出的新密钥对不上 | 派生只用了"本地方向的旧密钥" | 改用双方共享的 ECDH 秘密 + 角色标签 `i2r/r2i` |
| 18 | 换密钥瞬间在途消息被判"重放"直接断线 | 对端刚切新密钥，旧密钥发的帧还在路上 | 保留旧密钥 5 秒宽限期；能确认是过期计数的帧静默丢弃 |
| 19 | 轮换后消息永久卡住不发 | 发送队列 + 过期的 `_rekey_outstanding` + 不可重入的 `_order_lock` 互相等 | 改成标准 KeyUpdate（收到 begin 就切、用旧密钥回 ack、发起方收到 ack 再切），`RLock`，不再排队 |
| 20 | 用 PowerShell 文本命令改源码后中文全变乱码 | `Get-Content`/`Set-Content` 默认编码把 UTF-8 中文往返成了乱码，无法还原 | 用文件工具整体重写该文件；**规则：源码不经 PowerShell 文本管道往返** |
| 21 | 自测模式里预置了一道 `1+1=?` 并自动作答，看起来像"程序在演戏/有 bug" | 为了让第一次体验"有效果"，代码替用户预置了题目和提示，还留了一个"自己出的题自动作答"的隐藏逻辑 | 自测模式**只开两个正常窗口，不做任何预设**；删掉 `_auto_answer` / `_my_questions` 那套隐藏逻辑 |
| 22 | 答题时提示"请先选择一个人" | 「添加联系人」列表每 3 秒被广播刷新重建，`Treeview` 的选中项被清空，用户选好的人"掉了" | 列表用 `peer_id` 作为 `iid`，刷新前后记住并还原选中项；「新朋友」列表同样处理 |
| 23 | 程序重启后，答对的人被判成答错，一路错到自动封禁 | 出题方只在**内存**里留答案明文（`_question_answers`），重启后校验必然失败 | 校验改用**落盘的派生密钥** `K`（`answer_proof_matches_key`）：答案明文不落盘、不进内存，重启后照样判对 |

| 69 | 补发历史时**包特别大、还好认**（"中间人看到一大串大包就知道在同步记录，而且只解密这一个就能拿到之前所有的记录"）；另外还担心"轮换掉的旧密钥怎么还能解开历史" | ① 历史补发是"一大段明文塞进少数几个大帧"，帧大小和正常的聊天消息完全不是一个量级，抓包的人不用解密就能分类；② 聊天消息的长度本来就暴露（3 个字和半屏字长度差很多，甚至能猜到文件名多长）。至于"旧密钥"：其实**不存在这个问题** —— 内存记录里存的是**明文**，补发是用**当前**密钥重新加密的，轮换后旧的照样是废的 | 新增**长度混淆**：加密前把明文补齐到 512 字节的步长，**再随机加 0~一整个步长**（`PAD_RANDOM_EXTRA`，同一条消息连发 20 次会出现 18 种不同大小），填充来自 `os.urandom` 且一起被 AEAD 认证；解密侧丢掉填充字段，上层无感。另加**按需 zlib 压缩**（`crypto.seal_message`：只在不吃亏时才用，重复内容实测 8110 → 942 字节）；顺序是"先压缩再补齐"（反过来填充的随机字节会毁掉压缩率）。历史补发再叠加：**每帧最多 80 条** + 多帧之间**随机 50~250 毫秒**在后台线程发。明文 >16 KiB（文件分片）不补也不压。回归新增 `test_length_padding`（每次随机插、同步长内容看不出长短、压缩变小且解出来一字不差、大块不补不压） |

**教训总结**（已写进代码注释与测试里）：

1. **"窗口创建了" ≠ "窗口可见"**。必须检查 `winfo_viewable()` / Win32 `IsWindowVisible`，
   并用截图或窗口枚举验证；`tests/test_startup_window.py` 用子进程真实启动来守住这条。
2. **测试参数不能只走一条路径**。之前所有 GUI 测试都带 `--name`，恰好绕过了唯一有 bug 的分支。
   现在启动测试覆盖"不带参数 / 带参数 / --window-test / --self-test"四条路径。
3. **共享状态要有单一写入者**。socket 写、nonce 分配、入队都必须串行化，否则顺序会丢。
4. **控制台编码是中文 Windows 上 GUI 程序的必修课**，尤其打印特殊字符时。
5. **两端配置不一致时要有明确规则**。轮换频率、用途声明这类"双方都要同意"的东西，
   要么在握手时协商成一个确定值，要么定死谁说了算 —— 各用各的必然出问题（修复 #16、#47）。

> 说明：上表中的 `tests/` 测试脚本仅保留在本地开发环境，未随公开仓库发布。以下命令用于本地自测。

```bash
python tests/test_units.py              # 单元测试
python tests/test_rekey.py              # 密钥轮换 (零丢失验证)
python tests/test_integration.py        # 多实例联调 (本机同时起多个实例)
python tests/test_integration.py --only 1,3,5
python tests/test_gui_smoke.py          # GUI 冒烟
python tests/test_startup_window.py     # 启动窗口回归 (真实进程 + Win32 窗口枚举)
python tests/test_self_test_mode.py     # 自测模式自动化
```

联调测试是**真的**在本机同时启动多个实例、真的走 TCP 与加密握手：加好友 → 同意/拒绝/封禁/解禁
→ 三人互相加密聊天 → 1.5 MB 文件 SHA256 一致 → 把网线上抓到的字节捞出来搜，确认搜不到
明文消息、明文文件名和明文数据分片。

第 9 组是**封禁/解禁语义**（`--only 9`）：封禁好友 → 解禁后**仍然是好友**（不是删好友、
也不会凭空多出一条没答过题的『新朋友』请求）→ 对方收到『已解禁』通知并自动恢复加密会话；
被封的一方在重新申请时会被告知"你还在被封禁"；解禁后重新申请**仍然要先答对验证问题**。

第 10 组是**手动模式**（`--only 10`）：两个实例**完全不互相登记地址、发现层也互相看不到**
（用不同发现端口模拟"广播不通"），覆盖三种走法 ——
① 只填 IP → **单播探测**自动拿到对方 TCP 端口 → 直接加好友；
② 对方**隐身**时探测不到（明确失败）→ 改用 `IP:TCP端口` 直接连仍然能加上；
③ 在设置里把**本机端口**固定 → 重启后真的绑在那个端口上、对方也能按它加你。
另外还断言了"重启后联系人和地址都还在"。

## 13. 多语言（i18n）

界面语言：**简体中文（源语言）/ 繁體中文（台灣用語）/ English**。

### 13.1 为什么用"中文原文当 key"

`lanchat/i18n.py` 的 `t()` 直接拿**中文原文**当查表 key，而不是 `gui.send_button` 这种符号 key：

* 中文是源语言，**词条缺失时原样返回中文** —— 任何漏翻都不会让界面出现 `gui.send_button`，最差只是"这里还没翻到"；
* 代码里 `t("发送")` 一眼能看出这行显示什么，不用来回跳文件查 key 表；
* 代价：改了中文原文就等于改了 key，旧译文失效（退回中文）。所以**改文案时要同步改
  `lanchat/locales/*.py` 里的 key**，`tests/test_i18n.py` 会把"代码里有、目录里没有"的词条全部列出来。

### 13.2 代码里怎么写

```python
from .i18n import t

label = tk.Label(frame, text=t("发送"))                    # 静态文案
msg = t("已向 {0} 发出加好友请求, 等待对方确认…").format(name)   # 带参数: t() 本身不做格式化
```

**`t()` 不做格式化**（不带 `**kwargs`），插值统一写成 `t("…{0}…").format(...)`。这样帮助文本里
出现的花括号（JSON 示例之类）不会意外触发格式化，也就不会抛异常。

### 13.3 语言从哪来

优先级：`--lang` > `settings.json` 里的 `language` > 系统语言（`LANCHAT_LANG` 环境变量可覆盖，
测试用）。`chat_gui.py` 在 `check_environment()` **之前**就定好语言 —— 否则"缺少 cryptography"
这类启动失败提示会是中文，恰恰是最需要英文用户看懂的时候。

**切换是"重启后生效"**：界面上的字是建控件时一次性写进去的，运行时换语言要重建整棵控件树
（弹窗、菜单、已打开的对话框都得跟着重建），出错面比收益大。设置窗口里选完只落盘，下次启动生效。

字体按语言挑（`i18n.LANGUAGES[code]["fonts"]`）：简体 `Microsoft YaHei UI`、
繁体 `Microsoft JhengHei UI`、英文 `Segoe UI` —— Windows 上 Tk 不会自动回退字体，
用英文字体渲染中文会掉字。

### 13.4 词条目录与打包

* `lanchat/locales/en.py`、`lanchat/locales/zh_hant.py`，各自导出 `CATALOG = {中文: 译文}`。
* `i18n.CATALOG_MODULES` 是**写死的表**（不是拼字符串动态导入）—— PyInstaller 静态分析看不到
  拼出来的模块名，打包后会 `ModuleNotFoundError`；`lanchat.spec` 的 `hiddenimports` 里也要列上。
* 目录载入失败不会让程序起不来：捕获异常后退回中文（设 `LANCHAT_I18N_DEBUG=1` 会打印原因）。

### 13.5 测试

```bash
python tests/test_i18n.py      # 词条完整性 + t() 行为 + 语言优先级 + 落盘 + 三种语言真实建窗口
```

其中"词条完整性"是关键：它用 AST 扫出源码里所有 `t("…")`，逐条检查 en / zh-Hant 目录里有没有对应
译文，并校验英文里不含汉字、占位符与原文一一对应；"真实建窗口"则用 en / zh-Hant 各建一次主界面，
断言没有"本该翻却还是中文"的整条文案。
